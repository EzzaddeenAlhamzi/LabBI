# LabBI Requirements — Extracted from source DOCX

أولاً: التقرير التحليلي الكامل للمشروع

1. اسم المشروع

نظام إدارة وتداول الفحوصات المخبرية المدعوم بذكاء الأعمال

ويظهر في بعض مواضع الدراسة باسم قريب من:

نظام إدارة وتداول الفحوصات المخبرية والاتصال الذكي المدعوم بذكاء الأعمال.

التسمية الأولى هي الأنسب للاعتماد لأنها المستخدمة في عنوان مشروع التخرج نفسه.

2. فكرة المشروع

النظام عبارة عن منصة ويب تربط بين:

إدارة المختبر.

فنيي المختبر.

الأطباء.

المرضى.

والهدف هو تحويل دورة الفحص المخبري من دورة ورقية أو يدوية إلى دورة رقمية مترابطة.

النظام يبدأ من تسجيل المريض وربطه بمعرف طبي فريد، ثم إنشاء طلب الفحص واستقبال العينة، ثم إدخال أو استقبال نتيجة التحليل، وبعدها يقوم النظام بمراجعة النتيجة برمجياً لاكتشاف القيم الحرجة، ويعرضها ضمن أدوات ذكاء الأعمال، ثم يتم اعتماد النتيجة وإرسالها إلى الطبيب والمريض، وأرشفتها في الملف الطبي حتى يمكن الرجوع إليها مستقبلاً ومقارنتها بنتائج سابقة.

3. المشكلة التي يحلها النظام

الدراسة حددت تسع مشكلات رئيسية:

الاعتماد على العمل اليدوي وعدم وجود نظام إلكتروني موحد.

ضياع أو تلف التقارير الورقية وإمكانية الخطأ عند كتابة النتائج.

عدم وجود نظام آلي لاكتشاف القيم الطبية الحرجة.

بطء إيصال النتائج للطبيب والمريض.

ضعف أرشفة التاريخ الطبي وصعوبة مقارنة النتائج القديمة بالجديدة.

صعوبة مراقبة الإدارة لأداء المختبر.

ضعف الصلاحيات والأمان والتشفير.

عدم إمكانية أرشفة ملفات PDF والصور والتقارير المعقدة.

زيادة التكاليف التشغيلية والوقت الناتج عن العمل الورقي.

إذن المشروع ليس مجرد "نظام تسجيل تحاليل"، وإنما يفترض أن يعالج دورة تداول النتيجة بالكامل.

4. أهداف النظام

المشروع يسعى إلى تحقيق الآتي:

إرسال إشعارات عبر WhatsApp.

إرسال تقارير PDF للأطباء عبر البريد الإلكتروني.

الاحتفاظ بتاريخ الفحوصات.

مقارنة الفحص الحالي بالفحوصات السابقة.

توفير لوحات ذكاء أعمال.

توفير مؤشرات إدارية وتشغيلية.

تطبيق صلاحيات دقيقة.

تشفير البيانات الطبية.

تخزين المرفقات الطبية.

تقليل التكلفة والوقت والجهد.

6. المستخدمون الرئيسيون

7. دورة العمل الكاملة المقترحة للنظام

من تجميع جميع أجزاء المستند، دورة العمل المنطقية هي:

المريض → الطبيب → طلب الفحص → المختبر → استلام العينة → تنفيذ التحليل → إدخال/استقبال النتائج → التدقيق البرمجي → اكتشاف القيم الحرجة → مراجعة/اعتماد → إشعار الطبيب → إشعار المريض → إصدار PDF → الأرشفة → BI والتقارير.

وبالتفصيل:

المرحلة 1: تسجيل المريض

يتم تسجيل بيانات المريض وإعطاؤه:

Unique Medical ID / Medical File Number

ويستخدم هذا الرقم في ربط:

بيانات المريض.

طلبات الفحص.

العينات.

النتائج.

المرفقات.

التاريخ الطبي.

المرحلة 2: إنشاء طلب الفحص

يتم تحديد:

المريض.

الطبيب.

الفحص المطلوب.

تاريخ الطلب.

المختبر أو القسم.

حالة الطلب.

ثم يتم إرسال الطلب إلكترونياً للمختبر.

المرحلة 3: استقبال العينة

فني المختبر:

يستقبل الطلب.

يؤكد وصول العينة.

يطابق العينة بالطلب.

يبدأ المعالجة.

8. تنفيذ الفحص

بعد إجراء التحليل:

يتم إدخال النتائج يدوياً.

ويوجد في الدراسة أيضاً توجه نحو:

استقبال النتائج من أجهزة التحليل بشكل آلي.

لكن هذا الجزء يحتاج قراراً قبل البرمجة كما سأوضح لاحقاً.

9. محرك القيم الحرجة Critical Values

هذه إحدى أهم وظائف المشروع.

عند إدخال النتيجة، يجب أن يقوم النظام تلقائياً بمقارنتها بالقيمة المرجعية أو بالقيمة الحرجة المحددة لذلك الفحص.

مثلاً منطقياً:

Result = 180

بينما:

Critical Maximum = 150

يجب أن يقوم النظام مباشرة بتحديد النتيجة على أنها:

Critical

ثم:

إظهار تحذير.

تمييز النتيجة بصرياً.

تسجيل وقت اكتشافها.

إصدار إشعار للطبيب.

إدخالها في سجل الحالات الحرجة.

احتساب زمن الاستجابة TAT.

الدراسة تركز بقوة على الرصد الآلي للقيم الحرجة وتقليل زمن إرسال التنبيه للطبيب.

10. ذكاء الأعمال BI

ذكاء الأعمال هنا لا يعني أن النظام يشخص المرض.

بل يستخدم لتحليل البيانات التشغيلية والمخبرية.

يجب أن يوفر مثلاً:

عدد الفحوصات اليومية.

المكتملة.

قيد التنفيذ.

المؤجلة.

المرفوضة.

الحالات الحرجة.

أوقات الإنجاز.

متوسط TAT.

أداء المختبر.

تاريخ نتائج المريض.

مقارنة الفحص الحالي بالسابق.

مؤشرات الارتفاع والانخفاض.

مؤشرات لونية للقيم.

الدراسة تنص على إمكانية المقارنة الرقمية والتاريخية وعلى تقارير BI ولوحات تحكم، وفي موضع آخر توضح أن التحليل لا يشترط رسومات بيانية؛ لذلك يمكن أن تعتمد النسخة الأساسية على الأرقام والجداول والبطاقات والمؤشرات اللونية بالإضافة إلى الرسوم إن أريدت لاحقاً.

11. الإشعارات

يوجد أكثر من نوع إشعار.

الطبيب

بعد اكتمال الفحص:

يستقبل النتيجة.

في الحالة الحرجة يستقبل تنبيهاً فورياً.

المريض

عندما تصبح النتيجة جاهزة:

يستقبل إشعاراً فورياً.

يستطيع الدخول لمشاهدة سجله.

المستند يحدد البريد الإلكتروني والواتساب كقنوات اتصال رقمية أساسية.

49. الصياغة النهائية التي يمكن تسليمها مباشرة للمبرمج

المطلوب تطوير نظام ويب متكامل لإدارة وتداول الفحوصات المخبرية المدعوم بذكاء الأعمال، يخدم الإدارة وفنيي المختبر والأطباء والمرضى. يبدأ النظام من تسجيل المريض وإنشاء رقم ملف طبي فريد، مروراً بإنشاء طلب الفحص واستقبال العينة وتنفيذ التحليل وإدخال النتائج، ثم التدقيق الآلي للنتائج ومقارنتها بالقيم المرجعية والحرجة واكتشاف الحالات الحرجة تلقائياً وإطلاق التنبيهات، وصولاً إلى مراجعة واعتماد النتائج، إصدار تقارير PDF، إرسال النتائج والإشعارات للأطباء والمرضى، وأرشفة جميع البيانات داخل الملف الطبي للمريض.

يجب أن يتضمن النظام نظام مستخدمين وأدوار وصلاحيات RBAC، إدارة المرضى والأطباء وفنيي المختبر، دليل الفحوصات والقيم المرجعية والحرجة، إدارة طلبات الفحوصات والعينات والنتائج، المرفقات، محرك اكتشاف Critical Values، سجل التنبيهات، البريد الإلكتروني، تكامل WhatsApp، تقارير PDF، الأرشفة، المقارنة التاريخية للنتائج، لوحات ذكاء الأعمال، تقارير الأداء، احتساب زمن الإنجاز TAT، سجل العمليات Audit Log، والنسخ الاحتياطي والاستعادة.

يجب أن تكون الواجهة عربية وسهلة الاستخدام، وأن يطبق النظام حماية قوية للبيانات من خلال HTTPS والتشفير والصلاحيات وتخزين كلمات المرور بشكل آمن، مع منع SQL Injection وXSS وضمان عدم وصول أي مستخدم إلى معلومات لا يملك صلاحية عليها.

النظام في المرحلة الحالية Web-Based ولا يشمل إدارة المخزون أو المحاسبة المالية المعقدة أو التشخيص الطبي الآلي. ويجب أن تكون بنيته قابلة للتوسع مستقبلاً لإضافة مختبرات وأقسام جديدة وتطبيقات هاتف وربط مباشر مع أجهزة التحليل.
